  - **Mechanism:** `CheckRunner::run_check`'s `Err` arm fires only when cargo fails with no JSON line at all; a cargo process killed mid-run (OOM / user kill / disk-full rustc abort) that already flushed `compiler-artifact` JSON comes back `Ok` with `exit_ok = false` + a partial stream — `is_json_line` (a bare `starts_with('{')`) lets it past the Err arm. From the JSON alone that is indistinguishable from a clean pass. `fix_verify::verify`'s loop then merged zero error locations → empty `error_lines` → break → every still-applied edit tallied as kept. The baseline refused the same shape (`!exit_ok`) — the asymmetry was the tell.
  - **Same family, worse-shaped:** the `rustc_errors` driver's `check_all` — a killed initial check read `report.clean = true` (nothing to fix), and a killed recheck read `(0, 0)` on the Issue-100 lexicographic keep rule, the maximum decrease, keeping a fix nothing verified.
  - **Repair (one shared mechanism):** `CheckVerdict::check_verdict(exit_ok, has_error_diags)` in `compile_oracle` — `Incomplete` = non-zero exit with zero attributable diagnostics = refusal (restore everything + loud error, never a keep). Wired into both consumers; both driver Err paths already restored + reported. The completion-sentinel port the lead asked for: the check's exit status IS the sentinel.
  - **Already safe (audited, no change):** the clippy oracle lane (`bin/heal.rs` — `exit_ok=false` → no verdict, Heuristic, never Certified); `ClippyVerifier` (Issue-112 probe witness refuses an untrustworthy run); `rust_perf` verifier (Issue-112 keyed-package refusal; killed → `test_passes = false`); `measure_composite` (its `parse_unsafe` flag already encodes the shape). **Parent-kill residual stays documented** (fix_verify module docs): Ctrl-C mid-verify leaves exactly what `--fix --write` would have written — never worse than the non-verify path, but unverified.
